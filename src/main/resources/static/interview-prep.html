🔐 Secure Cloud Storage Back to App

Interview Preparation Guide

This page summarizes architecture, security, workflows, and interview-ready talking points for the Secure Cloud Storage project.

Project Purpose

The app provides cloud file storage where file content is encrypted before persistence. It uses a hybrid model: AES-GCM for file encryption and AWS KMS for encrypting/decrypting AES keys.

  • Backend: Spring Boot APIs (/api/files, /api/profile)
  • Storage: AWS S3 (encrypted files) + DynamoDB (metadata)
  • Identity: JWT-based auth via AWS Cognito issuer validation

Architecture & Data Flow

  1. Upload: generate AES key + IV, encrypt file bytes, encrypt AES key in KMS, upload ciphertext to S3, store metadata in DynamoDB.
  2. List: fetch metadata and filter by authenticated owner ID.
  3. Download: get metadata, fetch encrypted S3 object, decrypt AES key via KMS, decrypt content, stream to client.
  4. Delete: verify owner, remove from S3 and DynamoDB.

Security Model

  • Crypto: AES/GCM/NoPadding with 12-byte IV and authenticated encryption.
  • Envelope encryption: KMS encrypts/decrypts AES data key material.
  • AuthN/AuthZ: Spring Security JWT resource server, API routes authenticated by default.
  • Ownership checks: owner filtering for list and explicit owner verification on delete.
  • Quota: per-user 200MB limit before upload acceptance.

Main Files to Know

  • src/main/java/com/securestorage/SecurityConfig.java - auth rules + JWT resource server
  • src/main/java/com/securestorage/AwsConfig.java - S3, KMS, DynamoDB clients
  • src/main/java/com/securestorage/EncryptionService.java - AES/KMS encryption methods

Expanded Interview Questions (with concise answers)

  1. Why hybrid encryption instead of only KMS encrypt/decrypt file content? AES is efficient for large payloads; KMS is used to protect keys, reducing latency/cost for bulk data operations.
  2. Why AES-GCM? It provides confidentiality and integrity in one primitive, preventing silent tampering of ciphertext.
  3. How is key rotation handled conceptually? Re-wrap or re-encrypt stored data keys with new KMS keys and track key metadata/versioning in DynamoDB.
  4. How do you enforce multi-tenant isolation? Use JWT subject as owner ID and verify ownership on every read/write/delete path.
  5. What metadata is persisted and why? File ID, owner ID, S3 key, encrypted key, IV, type, and size are needed for secure retrieval and policy checks.
  6. Where is the biggest scalability bottleneck? Table scan + in-memory filtering during list operation; partitioned query patterns are preferred at scale.
  7. What are critical API hardening steps? strict ownership checks for download/read, validation of content type/size, and robust error handling.
  8. How does the frontend obtain and use identity? It receives Cognito token via redirect hash and sends it as Bearer token to protected endpoints.
  9. How would you improve observability? add structured logs/metrics around encryption latency, S3/KMS failures, and per-route error rates.
  10. How would you test security paths? negative tests for cross-user access, tampered IV/ciphertext decryption failure, and unauthorized JWT scenarios.
  11. How would you improve cost posture? lifecycle policies on S3 objects, DynamoDB access pattern optimization, and selective caching for metadata.
  12. What deployment concerns matter? secure secret handling, least-privilege IAM roles, region selection, and environment-specific configuration.
